# github-issue: 작업 전 이슈 생성 + 한글 라벨 + 워크트리

요청을 읽고 → 이슈 초안(제목·본문·라벨)을 만들어 → 사용자 확인 후 게시하고 → 그 이슈 전용 워크트리에서 작업을 시작한다.

분석 저장소에서는 "이 스크립트·수치가 왜 생겼는지"가 커밋만으로는 남지 않는다. 작업 전에 이슈를 만들어 두면 **요청(이슈) → 브랜치 → 커밋(`Refs: #번호`)** 이 한 줄로 이어져 나중에 추적할 수 있다. 커밋 자체는 `data-commit` 스킬이 맡는다.

## 언제 쓰고 언제 안 쓰나

| 상황 | 동작 |
|---|---|
| 새 기능·분석·데이터·시각화 추가, 버그/집계 오류 수정, 구조 개선 요청 | 이 스킬로 이슈부터 만든다 |
| "이슈 만들어줘", "라벨 달아줘", "상태 바꿔줘" | 이 스킬 |
| 질문·설명 요청 ("이 함수 뭐 하는 거야?") | 쓰지 않는다 |
| 오타·한두 줄 수정, 커밋/푸시만 하는 요청 | 쓰지 않는다 |
| 현재 브랜치가 이미 `<유형>/<번호>-...` 형식 | 새 이슈를 만들지 않고 그 이슈에서 계속 작업 |
| 같은 내용의 열린 이슈가 이미 있음 | 새로 만들지 않고 그 이슈를 쓸지 묻는다 |

한 요청에 서로 무관한 작업이 여러 개 섞여 있으면 이슈를 나눈다 (이슈 하나 = 브랜치 하나 = 설명 가능한 작업 단위 하나).

## 라벨 체계

이슈마다 **유형 1개 + 주제 0~2개 + 상태 1개**를 단다. 전체 목록·색·판별 규칙은 `references/labels.md`, 원본 데이터는 `references/labels.json`.

| 유형 라벨 | 커밋 type | 브랜치 접두사 |
|---|---|---|
| `기능` | feat | `feat` |
| `버그` | fix | `fix` |
| `데이터` | data | `data` |
| `분석` | analysis | `analysis` |
| `시각화` | viz | `viz` |
| `파이프라인` | pipeline | `pipeline` |
| `모델` | model | `model` |
| `개선` | refactor / perf | `refactor` |
| `문서` | docs | `docs` |
| `환경` | build / chore | `chore` |

- **주제**: `주제: 버스`, `주제: 노선`, `주제: 하차`, `주제: 정류장` — `data-commit`의 scope와 대응한다. 맞는 주제가 없으면 초안에 "새 라벨: `주제: OO`"라고 표시하고, 승인되면 `labels.json`에 추가한 뒤 동기화한다.
- **상태**: `상태: 대기` → `상태: 진행중` → `상태: 검토중` → `상태: 완료`, 그리고 `상태: 보류`. 한 이슈에 상태 라벨은 항상 하나만 둔다.

## 작업 절차

1. **현황 파악**
   ```powershell
   gh auth status
   git branch --show-current
   gh issue list --state open --limit 30
   ```
   로그인이 안 돼 있으면 사용자에게 `gh auth login`을 안내하고 멈춘다. 열린 이슈 중 같은 작업이 있으면 그 이슈를 쓸지 묻는다.

2. **라벨 준비** — 저장소에 없는 라벨만 만든다 (이미 다 있으면 아무 일도 하지 않는다).
   ```powershell
   powershell -NoProfile -ExecutionPolicy Bypass -File ".claude\skills\github-issue\scripts\sync-labels.ps1"
   ```

3. **초안 작성** — 요청과 관련 파일을 읽고 쓴다. 이미 작업한 변경이 있으면 `git diff --stat`도 참고한다.
   - **제목**: 한국어, 50자 내외, 마침표 없이 개조식 (`data-commit` 제목 규칙과 동일). `feat:` 같은 접두사는 붙이지 않는다 — 라벨이 그 역할을 한다.
   - **본문**: 아래 틀. 해당 없는 절은 뺀다.
     ```markdown
     ## 배경
     왜 필요한지, 지금 무엇이 문제인지 (버그면 재현 방법·기대 결과·실제 결과)

     ## 할 일
     - [ ] 구체적인 작업 단위
     - [ ] ...

     ## 데이터 기준
     기간·필터·집계 단위, 사용하는 파일 (분석·데이터 이슈일 때)

     ## 완료 기준
     무엇이 되면 끝난 것인지 (산출물 파일, 확인할 수치)
     ```
   - **라벨**: 유형 1 + 주제 0~2 + `상태: 대기`
   - **담당자**: 본인 (`gh api user --jq .login`)
   - **브랜치명**: `<접두사>/<이슈번호>-<영문-소문자-슬러그>` (예: `feat/12-stop-alighting-top10`). 슬러그는 3~5단어.

4. **초안 제시 (게시 전 확인)** — 아래 형태로 보여주고 승인을 받는다. 이슈는 공개 저장소에 바로 노출되고 알림이 나가므로 승인 없이 만들지 않는다.
   ```
   제목: 정류장별 하차 상위 10개 집계 추가
   라벨: 기능 · 주제: 정류장 · 주제: 하차 · 상태: 대기
   담당: @Blackbean23232
   브랜치: feat/<번호>-stop-alighting-top10

   (본문 전체)
   ```

5. **이슈 생성** — 한글이 깨지지 않도록 내용을 UTF-8 JSON 파일(scratchpad)에 Write 도구로 쓰고 `--input`으로 넘긴다.
   ```json
   {
     "title": "정류장별 하차 상위 10개 집계 추가",
     "body": "## 배경\n...",
     "labels": ["기능", "주제: 정류장", "주제: 하차", "상태: 대기"],
     "assignees": ["Blackbean23232"]
   }
   ```
   ```powershell
   gh api "repos/{owner}/{repo}/issues" --input <json파일경로> --jq ".html_url"
   ```
   `{owner}/{repo}`는 gh가 현재 저장소로 채워 주므로 그대로 쓴다. 출력된 URL 끝의 숫자가 이슈 번호다.

6. **워크트리에서 작업 시작** — 이슈 번호로 브랜치명을 확정하고 워크트리를 만든다. `EnterWorktree` 도구가 있으면 그것을 쓰고, 없으면:
   ```powershell
   git fetch origin
   git worktree add ".claude/worktrees/<번호>-<슬러그>" -b <브랜치명> origin/main
   ```
   이후 작업은 그 워크트리 경로에서 한다. 만들고 나면 상태를 바꾼다.
   ```powershell
   gh issue edit <번호> --remove-label "상태: 대기" --add-label "상태: 진행중"
   ```

7. **마무리** — 이슈 URL, 브랜치, 워크트리 경로를 알려주고 원래 요청한 작업을 이어서 한다. 커밋할 때는 `data-commit` 스킬이 브랜치명의 번호를 읽어 `Refs: #<번호>` 푸터를 붙인다.

## 상태 바꾸기

상태 라벨은 하나만 남도록 항상 이전 것을 지우고 새 것을 단다.

| 시점 | 명령 |
|---|---|
| 작업 시작 (워크트리 생성 직후) | `gh issue edit <번호> --remove-label "상태: 대기" --add-label "상태: 진행중"` |
| PR을 열었을 때 | `--remove-label "상태: 진행중" --add-label "상태: 검토중"` (PR 본문에 `Closes #<번호>`) |
| 병합·종료 | `--remove-label "상태: 검토중" --add-label "상태: 완료"` 후 필요하면 `gh issue close <번호>` |
| "보류해줘" | 현재 상태 라벨을 지우고 `--add-label "상태: 보류"` |

현재 달린 라벨은 `gh issue view <번호> --json labels --jq ".labels[].name"`으로 확인한다. 이슈를 닫거나 PR을 여는 것은 사용자가 요청했을 때만 한다.
